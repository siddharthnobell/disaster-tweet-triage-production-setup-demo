# Disaster Tweet Triage — Walkthrough

This document maps every file in the repo to the rubric section it belongs
to, explains why each one is structured the way it is, and gives the exact
commands to run each piece yourself, with the output you should see.

Run everything from the repo root. Commands are shown for PowerShell/bash —
`python -m scripts.xxx` works identically in either.

## One-time setup

```
pip install -r requirements.txt
```

This installs pandas, scikit-learn, scipy, sentence-transformers (+ torch/
transformers, which it pulls in), fastapi, uvicorn, joblib, pytest, httpx.
The sentence-transformers install alone is ~600KB, but the first time you
actually *use* `CandidateRepresentation` (Section B, training the
candidate), it downloads the ~90MB `all-MiniLM-L6-v2` model from Hugging
Face and caches it under `~/.cache/huggingface`. Every other command below
works fully offline.

Two things are **deterministic and gitignored**: `data/processed/`,
`models/`, `metrics/*.json` (top-level), and everything under
`data/incoming/`, `data/triaged/`, `logs/`, `monitoring/reports/`,
`metrics/archive/`, `metrics/retrain_candidates/` are regenerated by the
commands below and never committed. If you're running from a fresh clone,
run the sections in order (A → B → C → D) — each one depends on files the
previous one produced. Everything is seeded (`random_state=42`), so your
numbers should match this document exactly.

## Section A — Data & Features

### Files

| File | What it does | Why it's structured this way |
|---|---|---|
| `data/raw/train.csv` | The original Kaggle "NLP with Disaster Tweets" labeled data, 7,613 rows. | Never modified in place — everything downstream reads it and writes elsewhere, so this file is always the ground truth. |
| `src/feature_pipeline.py` | `clean_text()` (fixes HTML entities + a known mojibake encoding bug in this dataset + strips URLs), `dedupe_labels()` (resolves ~18 texts that appear more than once with conflicting labels via majority vote), `build_features()` (adds `cleaned_text` + 5 handcrafted features), `clean_and_featurize()` (both, in order). | This is the **one** module imported by everything else that touches raw text — training scripts, the FastAPI service, the ingestion job, the retraining job. If cleaning logic lived in two places, train-time and serve-time features could silently drift apart; this file makes that impossible by construction. |
| `scripts/build_features.py` | Runs the pipeline end-to-end on `data/raw/train.csv`, prints a summary, saves `data/processed/train_features.csv`. | The one-time data-prep entry point; everything after this reads the processed file, not the raw one. |
| `tests/test_feature_pipeline.py` | Unit tests for every cleaning/feature function, plus a sanity check against the real dataset (zero missing features, zero leftover mojibake). | |

The 5 handcrafted features (`word_count`, `has_url`, `hashtag_count`,
`mention_count`, `has_keyword`) are computed from the **raw** text/keyword
fields, independent of `clean_text()` — so URL-stripping in `clean_text`
never affects `has_url`, etc.

## Section B — Training & Evaluation

### Files

| File | What it does | Why it's structured this way |
|---|---|---|
| `src/data_split.py` | `make_splits()`: stratified 70/15/15 train/val/test split, seeded. | Split **once**, to disk, rather than inside each training script — otherwise the baseline and candidate could silently be scored on different rows, invalidating the comparison. |
| `scripts/make_splits.py` | Runs the split on `train_features.csv`, saves `data/processed/splits/{train,val,test}.csv`. | |
| `src/representations.py` | `BaselineRepresentation` (TF-IDF 1–2 grams + the 5 handcrafted features, concatenated) and `CandidateRepresentation` (frozen MiniLM sentence embeddings + the same 5 features). Both expose `fit`/`transform`. | The whole comparison only means something if the **only** thing that changes is how text becomes a vector. The 5 handcrafted features are identical on both sides on purpose. `CandidateRepresentation` doesn't fine-tune the encoder — only the downstream classifier trains — which is the standard cheap way to trial an embedding model. |
| `src/model_config.py` | `make_classifier()`: one `LogisticRegression` config used everywhere. | Same reasoning — representation is the only variable. |
| `src/evaluate.py` | `compute_metrics()` (accuracy/precision/recall/F1/ROC-AUC), `save_metrics()`. | Shared so baseline and candidate numbers are computed identically. |
| `src/train.py` | `fit_and_evaluate(representation, train, eval_splits)`: fits representation + classifier on `train`, scores on every split in `eval_splits`. | Extracted once a third consumer (`scripts/retrain.py`, Section D) needed the exact same fit/score logic as the two training scripts. |
| `scripts/train_baseline.py` / `scripts/train_candidate.py` | Load splits, call `fit_and_evaluate`, print metrics, save `models/{baseline,candidate}.joblib` and `metrics/{baseline,candidate}.json`. | Two near-identical scripts rather than one parameterized script — each is independently runnable/re-runnable (e.g. re-run just the candidate without retraining the baseline). |
| `src/promotion.py` | `should_promote(new_f1, current_f1, margin=0.01)`: is a new model's test F1 enough of an improvement to ship? | Small test sets (~1,100 rows) mean a marginal win could be noise, so the bar isn't "any improvement" — it's a fixed margin, shared with Section D's retraining gate. |
| `scripts/compare_models.py` | Loads both metrics files, prints a val/test comparison table, applies `should_promote`, prints a verdict. | |
| `tests/test_data_split.py`, `tests/test_representations.py` | Split-size/balance/determinism tests; `BaselineRepresentation` fit/transform tests on a tiny in-test corpus; a `@pytest.mark.slow` smoke test for `CandidateRepresentation` that skips gracefully if the model isn't cached. | |

## Section C — Serving & Inference

### Files

| File | What it does | Why it's structured this way |
|---|---|---|
| `src/predict.py` | `load_model()` (loads a joblib `{representation, classifier}` artifact), `predict_df()` (runs `build_features` + the model's representation + classifier on a dataframe), `predict_one()` (wraps it for a single tweet). | The **one** inference code path, imported by both the FastAPI service (real-time) and the ingestion script (batch) — they can never compute a prediction differently. |
| `app/schemas.py` | Pydantic request/response models (`TweetRequest`, `PredictResponse`, `HealthResponse`). | |
| `app/main.py` | FastAPI app. `GET /health` (503 if the model failed to load, instead of crashing at import), `POST /predict` (calls `predict_one`, logs the result via `src/prediction_log.py`). | Serves `models/baseline.joblib` — the model Section B kept. Because the candidate wasn't promoted, this service never imports torch/sentence-transformers at all: a real deployment-size win. |
| `src/prediction_log.py` | `log_prediction()`: appends one JSON line per request to `logs/predictions.jsonl`. | Feeds Section D — a human can later sample this log to produce new ground-truth labels for retraining. |
| `scripts/ingest.py` | `run_ingestion()`: scores every CSV in `data/incoming/` via `predict_df`, writes results to `data/triaged/`, moves processed inputs to `data/incoming/processed/` (so re-running never double-scores). | Directories and the model are function parameters (not hardcoded globals) specifically so tests can point this at a `tmp_path` instead of touching real data. |
| `tests/conftest.py` | `tiny_baseline_model` fixture: a small but real fitted `BaselineRepresentation` + classifier, so tests exercise the actual code path without depending on the gitignored `models/baseline.joblib`. | A fresh clone can run the full test suite before ever running `train_baseline.py`. |
| `tests/test_predict.py`, `tests/test_app.py`, `tests/test_ingest.py` | Unit tests for `predict.py`; FastAPI `TestClient` tests (health, predict, validation, 503-when-missing, logging); `run_ingestion` tests (scoring, file-moving, skip-bad-files, no-op). | |

On Windows, if you're re-running against a file that's already sitting in
`data/incoming/processed/` from a prior run, you'll hit:
FileExistsError: [WinError 183] Cannot create a file when that file already exists
This is because `Path.rename()` doesn't overwrite existing files on
Windows (it does on macOS/Linux). Fix: delete the stale file first
(`rm data/incoming/processed/<name>.csv`) and re-run — or, for a
permanent fix, change `scripts/ingest.py`'s `path.rename(...)` to
`path.replace(...)`, which overwrites on all platforms.

(The timestamp in the filename will be whatever moment you ran it — that's
expected, not a discrepancy.) `data/incoming/demo_batch.csv` has moved to
`data/incoming/processed/demo_batch.csv`; running `ingest` again immediately
prints `no new files in ...\data\incoming`.

## Section D — Monitoring & Retraining

### Files

| File | What it does | Why it's structured this way |
|---|---|---|
| `src/monitoring.py` | `detect_feature_drift()`: KS-test on numeric handcrafted features (`word_count`, `hashtag_count`, `mention_count`) vs. the training split; absolute rate-difference threshold on binary ones (`has_url`, `has_keyword`). `check_positive_rate_drift()`: compares the model's *predicted* positive rate on a batch against the training set's true positive rate. | Uses the same 5 handcrafted features from Section A as the drift signal — cheap to compute and doesn't need ground-truth labels, unlike real performance metrics (precision/recall), which need someone to label live tweets first. Predicted-positive-rate drift is a proxy for concept drift in the meantime. Batches under 30 rows are flagged `insufficient_sample` rather than silently trusted. |
| `scripts/monitor_batch.py` | CLI: `python -m scripts.monitor_batch <csv>`. Compares the batch against `data/processed/splits/train.csv`, prints a report, saves JSON to `monitoring/reports/`, **exits with status 1 if drift is flagged** (wireable into a cron job / CI check). | |
| `src/prediction_log.py` | (see Section C) | Also monitoring input — a human can review `logs/predictions.jsonl` to spot-check the live traffic represented in it. |
| `data/new_labels/batch_001.csv` | A mock "human reviewer corrected these after they were flagged" batch — 8 tweets, including fixing the exact "traffic jam disaster" tweet that Section C's demo misclassified. | Demonstrates the retraining feedback loop concretely rather than describing it abstractly. |
| `scripts/retrain.py` | `load_expanded_train()`: original `train.csv` + everything in `data/new_labels/*.csv`, featurized and deduped the same way as Section A. `run_retraining()`: retrains `BaselineRepresentation` + classifier on the expanded pool, evaluates on the **frozen** `val`/`test` splits, and only overwrites `models/baseline.joblib` / `metrics/baseline.json` if `should_promote` says yes — archiving the old model/metrics to `models/archive/` / `metrics/archive/` first. If not promoted, the candidate's metrics are saved to `metrics/retrain_candidates/` for audit, and production is untouched. | `val`/`test` are never touched by retraining — they stay exactly the splits `make_splits.py` carved out, so every retrain (however many there are over time) is judged against the same yardstick as every prior model. Only `train` grows. Paths/model are function parameters (like `ingest.py`) so tests run against `tmp_path`, never real artifacts. |
| `tests/test_monitoring.py` | Drift-detection tests on synthetic distributions (no drift, numeric drift, rate drift, insufficient-sample, positive-rate drift), plus a JSON-serializability regression test (a real bug hit during development: `numpy.bool_`/`float64` values silently breaking `json.dumps`). | |
| `tests/test_retrain.py` | `load_expanded_train` merge/dedupe tests; `run_retraining` promotion / non-promotion / archiving tests, using synthetic tiny splits and forced current-metrics values so the outcome is deterministic. | |
